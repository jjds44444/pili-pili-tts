# Pili Pili — Tabletop Simulator mod

Unofficial fan implementation of the card game **Pili Pili** (Ben, Martin & JB /
ATM Gaming) for Tabletop Simulator, currently seating 6. Python generates the
card art and emits a TTS save file; there is no runtime beyond TTS itself.
Everything - dealing, betting, scoring, cleanup - runs from in-world objects
(a round button, per-seat dibbers and dump zones); there is no floating UI
panel.

## Build

```bash
python build_save.py                    # render art + install; images served from this repo
python build_save.py --skip-art         # reuse assets/, just rebuild the JSON (seconds not minutes)
python build_save.py --local            # file:/// images instead - host-only, but instant
python build_save.py --out DIR          # write save + assets somewhere else
python validate.py <path>/PiliPili.json # structural check before loading in TTS
python layout_preview.py <path>.json    # top-down map of table positions, checks overlaps
python preview.py preview.png           # contact sheet for eyeballing the art
```

Images are served straight from this repo's `assets/` by default, so a plain build
is already multiplayer-ready - remember to commit and push `assets/` after any art
change, or everyone but the host keeps seeing the old cards.

Requires Python 3, Pillow and numpy. A full art render is ~90s for 106 faces;
use `--skip-art` whenever you are only changing the save structure.

## Layout

| File | |
|---|---|
| `build_save.py` | Assembles the TTS save JSON. Entry point. |
| `art.py` | Card faces, backs and token. Layout, palette, typography. |
| `glyphs.py` | Tribal glyph vocabulary and the hand-cut edge treatment. |
| `missions.json` | The 36 mission cards — data only, safe to edit. |
| `global.lua` | TTS table script: dealing, betting, Pilis, cleanup. |
| `validate.py` | Structural checks on a generated save. |
| `preview.py` | Contact sheet of the rendered art. |
| `layout_preview.py` | Top-down map of a built save's table positions, with an overlap/off-felt check. |
| `assets/` | Generated PNG sheets, regenerated by `art.py` - except `ATM_GAMING_pilipili_RULES.pdf`, the real published rulebook, which is a static file (see Scope below). |

## How the art works

Matched to the published cards: flat colour bands by value (blue → cyan → green
→ yellow → red, see `BANDS`), a big centre numeral in white with a heavy black
keyline and tribal ink marks inside the digit shapes, indices in all four
corners, and a field of scattered glyphs in a darker tone of the card colour.
Missions are pale with a solid ink pictogram and the deal count in a dark box
bottom-left; backs are black with a flaming mask over crossed chillies. Every
face and back goes out through `framed()`, which adds the published cards'
heavy black rounded border - it scales the art down into the inset rather
than painting the frame over the top, because the corner indices sit close
enough to the edge that painting over would clip them.

`glyphs.py` is the interesting part. Silhouettes (mask, totem, figure, sun,
chilli, hand…) and interior marks (chevrons, dot rows, zigzags, hatching, eyes,
teeth) compose into a distinct glyph per card, seeded deterministically by card
number. `roughen()` is what stops it looking machine-drawn: it blurs a mask into
a ramp and thresholds it against low-frequency noise, so every contour wobbles.
`NAMED` holds purpose-built mission pictograms (arrows ring, stopwatch, ban,
swap, forehead…) and `MISSION_ICONS` in `art.py` maps mission titles onto them —
add a mission title there or it falls back to a random glyph.

Everything renders at `SS` × size and downsamples; the rough edges need the
resolution. Dropping `SS` to 1 makes iteration fast but looks bad.

## Table layout

**The table is `Table_Circular`.** It went `Table_Poker` -> `Table_Custom`
(Custom Rectangle) -> here across three sessions; see git history for the
poker table's stadium-shape problems and the rectangle's own reasoning if
either is needed again. The rectangle fixed the poker table's bugs but read
as "big and soulless" in practice - two dead short ends and a wide-open
middle with nothing to draw the eye - and its 3-per-side seating meant every
player had two neighbours at a slightly different distance. A true circle
has neither problem, and - unlike the poker table's straight-vs-curved split
- has no per-seat exception to get wrong either: every seat's own radius
vector already is the correct "inward" direction, uniformly, no distant
reference point or per-corner fix needed.

**`Table_Circular` cannot take a custom surface image.** Confirmed against
the one real `Table_Circular` mod installed locally: it has no `TableURL`
key at all, unlike `Table_Custom`/`Table_Custom_Square`. The tribal felt
built for the rectangle (`felt()` in `art.py`) is kept - harmless, and useful
again if a Custom table ever comes back - but nothing in `build_save.py`
references it now. What's actually on the table is TTS's own stock circular
surface, whatever that looks like; nobody here has seen it yet (see
"Verified so far" below).

`SEATS` in `build_save.py` is generated from `_seat_xz(phi)`, not written out
by hand: `x = -FELT_R * sin(phi)`, `z = -FELT_R * cos(phi)`, for six `phi`
values 60 degrees apart. `FELT_R` (21.51) and `HAND_W`/`HAND_D` (11.7 x 6.8)
are real, averaged from the 8 HandTriggers of "Auto replace Imgur links with
mirror site" - a genuine, working `Table_Circular` mod, the only one
installed locally. That mod seats 8, not 6; **this is the one weaker link in
the chain** - there was no 6-seat `Table_Circular` mod to lift coordinates
from directly, so 6 are evenly redistributed round the same real radius
instead. That's a smaller leap than guessing the table's geometry outright:
`_seat_xz()`'s formula reproduces all 8 of that mod's real positions exactly
(rotY included - the reference mod's own HandTrigger rotY equals `phi`
directly, not a separate value), so it's the placement *formula* that's
proven against real data, not just one seat count's worth of coordinates. If
a genuine 6-seat `Table_Circular` mod ever turns up, check its coordinates
against what `_seat_xz()` currently produces before assuming either is right.

**`FELT_R` is weaker evidence than the rectangle's `FELT_X`/`FELT_Z` were.**
The rectangle had an independent community measurement (7'4" x 4'4") to
cross-check its felt size against. There is no equivalent independent
measurement for `Table_Circular` - `FELT_R` is inferred from where the
reference mod's real hand zones sit, not measured separately. Treat it as
provisional until an in-game ruler check confirms or corrects it, and update
`FELT_R` in both `build_save.py` and `layout_preview.py` together (they must
match) if it turns out to be wrong.

**No more trick mat or Pili tray - one open "dump zone" per seat, shared by
both token kinds.** See "Trick and Pili tokens" below for why; the layout
consequence is that each seat now has only two footprints to place (dibber,
dump zone) instead of three, which is what let both sit closer to the seat's
own edge of the felt than the rectangle's dibber/tray ever did - requested
explicitly ("closer to the edge of the table a little bit") and delivered by
having one less thing to clear, not by cutting the margins on what's left.

**`seat_spot()`'s geometry is genuinely polar now, not the rectangle's
straight-toward-z=0 special case.** `inward = (sin phi, cos phi)`,
`tangent = (cos phi, -sin phi)`, where `phi` is the seat's own rotY -
reproduces `_seat_xz()`'s own formula when `out=0`, and is what makes a
seat's "in front of" and "sideways from" consistent with its actual position
on the ring at any angle, not just the rectangle's 0-or-180. `felt_clamp()`
is a plain radial clamp (`hypot(x,z) <= FELT_R - margin`) - exact given
`FELT_R`, no stadium/rectangle-corner approximation needed on a true circle.

**`OUT_CTRL`/`SIDE_DUMP`/`DUMP_HALF` were found with a real rotated-footprint
search, not the rectangle's simpler axis-aligned one.** A first pass here
reused the rectangle's kind of search - treating each footprint as an
axis-aligned box - and it produced numbers that looked feasible under that
approximation but had genuine overlaps once actually built and checked
against real, rotated rectangles (`layout_preview.py`'s `corners()`/
`polys_overlap()` - see below). Seats packed 60 degrees apart, at the radius
these footprints sit at, are close enough that a rotated tile's true reach
differs meaningfully from its unrotated half-width; the axis-aligned
approximation the rectangle table could get away with (every seat's rotY was
0 or 180 there, so "axis-aligned" and "true footprint" were the same thing)
stops being safe once rotation is a real angle. If `SEATS`, `HAND_W`/
`HAND_D`, or these scales change, re-run a search against
`layout_preview.py`'s own `corners()`/`polys_overlap()` - not a simpler
axis-aligned check - or trust `layout_preview.py`'s own overlap report
directly and iterate against that.

**`face_centre(x, z)`** generalises `SEATS`' own rotation formula to objects
that aren't tied to a seat (Next Round, New Game, the missions toggle, the
rulebook) - the rectangle table's first pass here shipped all three at a
lazy `rot_y=0.0` and had them facing away from the table; this works out the
correct rotY from the object's own position instead of inheriting a default.
Next Round and New Game deliberately share ONE rotation (their cluster's own
midpoint, not each tile's own slightly different angle) rather than each
computing its own - so the pair reads as one matched control, and so neither
tile's rotated footprint reaches further toward its neighbour than its plain
half-width would suggest (an off-axis rotation on two adjacent square tiles
otherwise makes them reach further towards each other along the diagonal
than an axis-aligned check would predict - this is exactly the kind of thing
the rotated-footprint search above exists to catch, and is a good worked
example of why the axis-aligned approximation isn't safe here).

**A `Custom_Tile`'s shape comes from its IMAGE, not from `scaleZ`.** TTS
works out the rendered shape from the source image's own aspect ratio;
`scaleX`/`scaleZ` are a uniform size multiplier on top of that. Verified
against real workshop tiles that ship non-square art - a Type 3 tile with a
1520x478 image (3.18:1) at `scaleX = scaleZ = 1.5`, Type 0 tiles at 1600x700
and 3355x2040, all with equal scales - and across 451 real `Custom_Tile`s
checked, every single one has `scaleX == scaleZ`. **So: want a rectangular
tile? Draw a rectangular image and leave the scale uniform.**

This file previously asserted the exact opposite ("TTS renders `scaleX`/
`scaleZ` as literal, independent width/depth and does NOT infer them from
the image"), and `custom_tile()` set `scaleZ = scale * aspect` accordingly -
applying the aspect a second time on top of the one TTS already applies, so
any non-square tile came out squashed flat. That wrong note is what made
"square canvases throughout, deliberately" look like a law of nature rather
than a workaround for a local bug, and it burned a lot of time: the squish
got blamed on non-square canvases, then on GitHub's CDN, then on TTS's
caching, then on stale save files - none of which were it. **When a
rendering result contradicts a note in this file, suspect the note.**

**Check any layout change** with `python layout_preview.py <path/to/PiliPili.json>`
before loading it in TTS - it draws every object at its real, *rotated*
footprint (`corners()` + a proper SAT `polys_overlap()`, not a simpler
axis-aligned box check - see above for why that distinction now matters) and
fails if anything overlaps, sits off the felt, **or sits inside a hand
zone**. Tuning against this cut a multi-minute TTS-screenshot loop down to
seconds, and the hand-zone check is what would have caught the Pili-into-hand
bug before it ever reached a real game.

## Things that will bite you

**Deck sheets are grids.** A TTS `CustomDeck` is one image of `NumWidth × NumHeight`
card faces, and `CardID = deckId * 100 + indexOnSheet`. The play deck is 8×7 = 56
slots holding exactly 56 cards; missions are 6×6 = 36. Adding a mission past 36
overflows the sheet — bump the grid in `art.generate()` and the `custom_deck(...)`
call in `build_save.py` together, or cards silently render as the wrong face.

**The Lua finds everything by GMNotes, not GUID or Nickname** - and **`one(tag)`
promises nothing about *which* same-tagged object it returns if there's more
than one.** Decks get merged and re-created constantly during play, so GUIDs
are worthless. Every tagged object carries a `PILI:` prefix -
`PILI:PLAY`/`PILI:MISSION` on cards and decks, `PILI:DIBBER:<colour>`/
`PILI:DUMP:<colour>`/`PILI:DUMPTILE:<colour>` per seat, plus `PILI:BUTTON`,
`PILI:NEWGAME`, `PILI:DEALER`, `PILI:BAG`, `PILI:TRICKBAG`, `PILI:MTOGGLE`.
**`PILI:DUMP` and `PILI:DUMPTILE` used to be one shared tag** on the theory
that only the `ScriptingTrigger` was ever functionally needed, so a second
bookkeeping-only tag on the backdrop tile would have no purpose - true, but
`one(TAG_DUMP .. colour)` (`tagged(tag, true)[1]`) doesn't guarantee it
returns the zone rather than the tile, and in a real load it returned the
tile: `getObjects()` doesn't exist on a plain `Custom_Tile`, so
`sweepAndDeal()` crashed with "attempting to call getObjects() on an object
that does not support getObjects()" the first time a seat's dump tile won
that race. Split back into two tags - `PILI:DUMP` is the zone the script
actually queries, `PILI:DUMPTILE` is the backdrop's own separate,
script-unused tag - the same mat/tray-vs-tricks/pilis split the rectangle
table used, and for the same reason. **Any tag two objects can legitimately
share is a bug waiting for `one()` to pick the wrong one** - give the object
the script actually needs to find a tag nothing else on the table carries.
`gather()` re-stamps the play/mission tag after merging a pile back together.
`validate.py`'s "in-world controls" section checks every seat has its full
set - keep that invariant or the round button silently stops finding a
seat's objects.

**Mission deal counts live in the card Description** as `[deal N]`, parsed by
`dealCards()` (called from `sweepAndDeal()` whether or not a mission was
actually drawn). `build_save.py` appends it; don't strip it.

**Missions default OFF** (`missionsOn = false`), toggled by the `PILI:MTOGGLE`
tile's button - matches the rulebook's own "first game" suggestion (deal 5,
skip missions). `sweepAndDeal()` branches on it before touching the mission
deck at all when off; the mission deck is completely untouched in that case,
not just hidden.

**Tricks are scored by token, not by counting cards.** The old design had
the trick's winner physically stack the actual played cards on their own
mat, and the script inferred tricks won as `cards on the mat / seat count` -
reported as broken in real play: no error correction (an incomplete or
mixed-up pile just silently fed the wrong number into that division), and
the storage was far too small for what a bad run of tricks could pile up.
Now a resolved trick's cards go to the shared discard (players do this
themselves, same as before - the script still never has to work out who won
a trick, which is what keeps every mission that rewrites trick resolution
entirely out of its business) and the winner drags one token out of
`PILI:TRICKBAG` into their own dump zone. `trickCount()` in `global.lua`
just counts `PILI:TRICKTOKEN` objects there - a token either landed in your
zone or it didn't, nothing to miscount. `sweepAndDeal()` clears trick-tokens
back out (`.destruct()`, not returned to the bag - it's an `Infinite_Bag`, so
there's nothing to conserve) at the start of every new deal; Pilis in the
same zone are untouched by that sweep.

**Pilis are dished out automatically but the game no longer ends itself.**
`givePilis()` is unchanged - the script still spawns Pili tokens into the
loser's dump zone automatically when a bet is missed. What used to be
`checkGameOver()` gated `nextRound()` automatically once someone hit
`PILI_LIMIT`; that gate is gone. `PILI_LIMIT` is now just a number for the
players to judge by themselves, hand-tracking the pile of tokens in each
dump zone - `PILI:NEWGAME` (`newGame()`) is a manual reset a player presses
once they've agreed someone's lost, which announces standings
(`standingsMessage()`) and clears every `PILI:TOKEN` on the table. This was
a deliberate request, not a bug fix: automatic detection had no way to
correct for a miscounted pile either, same complaint as the old trick
scoring, so scoring stayed manual/social on purpose rather than trading one
silent-miscount failure mode for another.

**Resting community piles are locked, not just positioned.** On the old poker
table the play deck was reported drifting off the table entirely - its home
sat deep in the dealer's open cut-out, the one edge that table left unrailed,
so a physics nudge from anything nearby could walk it right off the felt.
Every table used since (the rectangle, now the circle) is railed on every
edge, so that specific failure mode shouldn't recur, but `lockAtRest()`/
`unlockForOps()` in `global.lua` still pin every shared pile (play deck,
mission deck, discard) once it settles, and unlock it
again immediately before the next scripted `.shuffle()`/`.deal()`/
`.takeObject()` call, as a second line of defence. Add a new shared pile
without this pattern and it can still walk off under a strong-enough nudge,
rail or no rail.

**`HideWhenFaceDown` belongs on cards and nothing else.** It hides a
face-down object's identity behind TTS's generic "?" placeholder - correct
for a card, wrong for everything else. `BASE_FLAGS` used to set it `True`
for every object this file builds, so flipping a Pili token over turned it
into a question mark (reported from a real game). Real-mod convention is
unanimous: all 425 `Custom_Token`s, all 493 `Custom_Tile`s, all 51
`Custom_PDF`s and all 45 `Infinite_Bag`s checked across 28 mods have it
`False`; only cards ever set it `True` (64 of 111). `BASE_FLAGS` now
defaults to `False` and `card()`/`deck()` set it `True` themselves.

**Every `Custom_Token`'s `ImageSecondaryURL` is empty, always, even for
one-shot tokens with a genuinely blank back** - confirmed against all 452
tokens across 28 real workshop mods, `Stackable` true or false. TTS mirrors
the front onto the back itself, so a token looks the same whichever way up
it lands. Don't set `ImageSecondaryURL` on a `Custom_Token` unless you
actually want a *different* back image - in particular, don't reach for it
to fix a blank/"?" back, which is the `HideWhenFaceDown` problem above.

**The seating order is injected into the Lua at build time**, not written in
`global.lua` itself - `build_save.py` prepends `SEAT_ORDER = {...}` (from `SEATS`)
plus the shared `POS_*` constants before the rest of the script. Don't hand-edit
positions or seat order into `global.lua`; change the Python and rebuild, or the
two will drift apart.

**Validate before loading.** TTS fails silently and unhelpfully on a malformed save
- a bad `CardID` gives you the wrong card face, a `ScriptingTrigger` missing
`LuaScript`/`LuaScriptState`/`XmlUI` fails the ENTIRE load with a bare "Object
reference not set to an instance of an object" naming no object at all. That one
cost real time before a diff against real Tabletop Simulator workshop mods (in
`Mods/Workshop/*.json` if the user has any installed) turned up the missing
fields - when in doubt about what a TTS object needs, check a real save rather
than guessing. `validate.py`'s "required fields" section now asserts this class
of field is present on everything.

## Scope

**Public repo**, at github.com/jjds44444/pili-pili-tts. Fan implementation, no
affiliation with the publisher, and the README says so.

Matching the published cards' *look* is the goal and reference photos are fine
for that. Card art specifically must stay generated by `art.py`/`glyphs.py`,
never a scan or export of the real cards - that would be redistributing the
publisher's artwork rather than referencing it. Draw it in code instead.

**The one deliberate exception**: `assets/ATM_GAMING_pilipili_RULES.pdf` is the
actual published rulebook, not a redraw. This is a real, explicit call the user
made knowing what it means - hosting the publisher's own copyrighted document
from a public repo, not just referencing it - after being offered a host-only
`file:///` alternative that would have avoided that. Don't "fix" this by
regenerating it from `art.py`, and don't extend the same treatment to the card
art or anything else without asking first; this exception was scoped to the
rulebook specifically, not a general license.

Attribution to Ben, Martin & JB / ATM Gaming appears in the README, the
rulebook object itself, and the save description. Keep it.

## `missions.json` is a reconstruction

The official rulebook (pp. 14–19) prints the
17 mission *effect types* but never the parameters of the 36 individual cards: how
many cards each deals, which way the pass arrows point, how many cards move, which
numbers are cursed. The current split covers all 17 effects plausibly. If someone
turns up with the physical deck, correcting `missions.json` and rebuilding is the
whole fix — don't restructure code for it.

## Verified so far, and what is not

Real Tabletop Simulator play (not just `validate.py`) on the *old* poker
table found and fixed a real list of bugs - oversized/cramped tiles, Pilis at
risk of landing in a hand, a blank token back, the dealer marker sitting on
the dibber, corner seats facing the wrong way, and the play deck drifting off
the table - all root-caused against real data (28 workshop mods' worth of
genuine TTS objects, not more guessing). None of that is the current table.

A brief, unplayed load of the *rectangle* table (`Table_Custom`) caught two
more real bugs before it was replaced in turn: a first felt-art attempt that
read as a wall of clip-art rather than a texture (too dense/sharp/
high-contrast for a canvas this much bigger than a card), and the rulebook/
missions-toggle plaques facing away from the table instead of into it. Both
fixed on the rectangle; neither claim survives the table switch below, since
the objects and their placement logic changed again.

**`Table_Circular` - the current table - has been loaded in TTS at least
twice now.** The first load found the real `one()`/shared-tag bug described
above (`PILI:DUMP` vs `PILI:DUMPTILE`, crashing `nextRound()` outright) and
two placement complaints (dibber/dump zones not close enough to the edge,
the rulebook too far toward the centre). A second load, after fixing all
three, confirmed the crash is genuinely gone - `nextRound()`/`newGame()` ran
far enough to show both buttons and Next Round actually executing - but
turned up a fresh, real bug of its own: `Custom_Tile` squishing a non-square
canvas in play (see "Every real Custom_Tile is square" above), now fixed by
going back to a square tile with the rectangle look painted on
(`nameplate()`). **That specific fix has not been re-loaded into TTS to
confirm it looks right there** - see the note two paragraphs up for exactly
this pattern happening before (rectangle table, bugs fixed after one brief
load, "neither claim survives" once the table changed again; same caution
applies to any single fix here until the *next* load confirms it). Still not
confirmed even by the two loads so far: whether `FELT_R` (inferred, not
independently measured - see the caveat under "Table layout") matches the
real in-game boundary, whether hand zones actually catch a dealt hand on
this table, and which seat colour physically lands at which of the six
positions.

**The token-based trick/Pili scoring and the manual New Game reset have been
loaded but not actually played** - the crash-fixed second load got as far as
rendering both buttons correctly-functioning-looking, but nobody has
actually run a bid/trick/score cycle through them yet. Specifically
unconfirmed: `trickCount()`/`piliCount()` actually counting the right
objects out of the zone now that `one()` has only one candidate to return,
`sweepAndDeal()`'s trick-token cleanup not also catching Pilis it shouldn't
touch, and `newGame()`'s `.destruct()` loop actually clearing every seat
rather than
silently missing one.

Still not confirmed even before any of this: a full round end-to-end
(bidding through scoring through someone actually pressing New Game), the
"bets must not total the cards dealt" rule actually tripping in practice,
and whether the new discard-and-token trick flow feels right at the table
compared to the old physical-card-pile one it replaced.
